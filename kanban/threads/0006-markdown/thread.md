## 决策

- **决定**：采用 Marked + DOMPurify 的 vendored 浏览器 ESM 构建，统一提供安全 Markdown 渲染。
  **原因**：两者成熟且适配现有无构建前端；Marked 支持所需 GFM 语法，DOMPurify 负责清理渲染输出，避免各编辑入口分别实现安全策略。
- **决定**：线程各小节、全局便签和新建线程目标均提供编辑即时预览，Markdown 原文仍是唯一存储格式。
  **原因**：覆盖全部现有入口可保持一致交互；渲染 HTML 不落盘，现有读写接口和数据格式无需改变。
- **决定**：既有线程小节和便签在停止输入约 800ms 后自动保存，新建线程目标仍在创建时保存。
  **原因**：既有文档具有指纹和写接口，可安全复用乐观并发；新建目标尚无持久化对象，创建前只保留草稿更符合现有流程。
- **决定**：通过可见页面每约 2–3 秒的指纹轮询自动读取其他来源的变更，页面隐藏时暂停，重新可见或获得焦点时立即读取。
  **原因**：现有 GET 接口已能覆盖 Agent、文本编辑器和其他窗口的修改；相比 fs.watch + SSE，无需处理操作系统监听语义、断线重连和额外服务生命周期，也不会让隐藏页面持续保活服务。
- **决定**：采用 node-diff3 基于共同基准、本地草稿和外部版本进行三方合并；仅无冲突结果自动采用并保存，有冲突时暂停自动保存并人工处理，且不向文件写入冲突标记。
  **原因**：普通编辑器和 Agent 不参与 Yjs、Automerge 等 CRDT 文档模型，三方合并才符合任意外部写文件场景；冲突时保留双方内容并交由用户决定，可避免静默覆盖。
- **决定**：首版不引入 CodeMirror MergeView、Yjs、Automerge、SSE 或完整 Markdown 编辑器。
  **原因**：这些方案需要额外编辑器模型、构建加载或服务通道，当前需求可由轻量渲染、现有接口和三方合并覆盖，引入后维护成本大于收益。
- **决定**：可编辑预览中的 GFM 任务复选框允许点击并更新 Markdown 草稿，只读与冲突外部版本保持禁用；按 Marked token 顺序定位源标记并复用现有 `setDraft`。
  **原因**：用户需要在便签预览中直接切换任务；token 定位可避免误改代码块或嵌套任务，复用草稿入口可继续遵循既有防抖保存、指纹与冲突处理，无需新增写接口。
