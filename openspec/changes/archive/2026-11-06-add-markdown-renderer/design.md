# Design

## Context

现有前端使用 vendored Preact + htm，无构建步骤；线程详情和便签通过现有 GET/PUT 接口读写原始 Markdown，并以整个文件的 SHA-256 指纹执行乐观并发。线程详情一次只允许编辑一个小节，便签是单文档编辑，新建目标在创建前没有持久化对象。服务已提供原子写盘、409 和 P4 checkout，外部写者可直接修改文件而不经过网页。

## Goals / Non-Goals

**Goals:**

- 以少量 vendored 模块完成安全渲染、即时预览、自动保存、外部读取和三方合并。
- 将并发与异步状态集中管理，避免线程和便签分别实现后出现覆盖语义差异。
- 保持现有 API、文件格式、服务生命周期和发布方式可用。

**Non-Goals:**

- 不实现多人光标、在线状态、操作级协同、自动语义冲突识别或完整所见即所得编辑器。
- 不引入文件监听、SSE、WebSocket、CRDT、Service Worker 或服务端合并 API。
- 不保证浏览器崩溃、强制关闭或操作系统断电前完成尚未发出的保存。

## Decisions

### 1. 集中安全渲染，保留 textarea 编辑模型

新增前端 Markdown 模块，vendored 固定版本的 Marked 浏览器 ESM 与 DOMPurify ESM。Marked 启用 GFM；其输出必须先经 DOMPurify 清理，再交给唯一的 Preact HTML 插入点。清理配置仅允许 HTML profile，禁止样式和其他非必要活动内容；清理能力不可用或渲染异常时回退为 Preact 转义文本与错误提示，不插入未清理 HTML。

新增共享预览组件，阅读模式和编辑模式复用同一渲染入口。编辑时桌面端左右分栏、窄屏上下排列；保留 textarea，不引入 CodeMirror。`## 依赖` 阅读模式仍由现有专用组件处理，编辑预览才使用通用 Markdown 渲染。

备选方案是 CodeMirror MergeView 或完整 Markdown 编辑器，但其构建加载、样式和编辑器状态成本超出首版需求。

### 2. 用显式文档状态串行化自动保存

新增可复用的文档同步控制器，由线程小节和便签适配现有 API；新建目标只使用预览，不创建控制器。每个编辑会话至少维护：

- `baseContent` / `baseFingerprint`：最近共同确认的内容与整文件指纹。
- `draft` / `revision`：当前草稿及单调递增的本地修订号。
- `inFlight`：唯一进行中的保存及其修订号。
- `status`：`dirty`、`saving`、`saved`、`error`、`conflict`。
- `remote`：检测到但尚未解决的外部快照。

输入后约 800ms 触发保存，内容相对最近共同基准未变化时不请求。保存期间的新输入只增加修订号；旧响应可推进共同基准，但不能替换更新的草稿，完成后保存最新草稿。任何时刻不并行写入同一编辑会话。

「完成编辑」、关闭便签和离开当前详情调用同一 `flush()`：立即取消防抖等待并尝试保存，失败时保持编辑或模态框上下文。自动保存后不再提供“取消并恢复”的假象，已有内容只能通过后续编辑或冲突处理改变。

### 3. 可见页面使用现有 GET 做有界轮询

轮询间隔定为 2500ms，仅覆盖当前项目线程列表、当前详情和已打开便签。每个资源最多一个进行中的读取；root、线程或模态框切换时以代次标识忽略旧响应。`visibilitychange` 恢复可见和窗口 `focus` 时立即检查，隐藏时清理计时器并暂停新请求。

响应指纹与最近共同确认指纹一致时不更新内容状态。列表轮询只更新列表投影，不重建详情编辑器。可见轮询沿用成功业务交互保活语义，隐藏页面不会通过轮询延长服务寿命。

备选方案是 fs.watch + SSE，但其跨平台原子改名语义、动态项目监听、连接恢复和额外服务状态不适合当前本地小文档场景。

### 4. 以共同基准协调外部读取和自动保存

外部快照按以下顺序协调：

1. 本地无未保存修改：采用外部内容、指纹和列表投影。
2. 外部指纹来自刚完成的本地保存：按本地保存响应处理，不误报外部冲突。
3. 正在编辑线程小节，且外部该小节仍等于 `baseContent`：采用外部其他小节与最新指纹，保留当前草稿并继续保存。
4. 外部当前内容等于本地草稿：视为双方收敛，采用外部指纹并标记已保存。
5. 外部当前内容也发生变化：以 `baseContent`、当前 `draft`、外部当前内容执行三方合并。

保存进行中收到的外部快照先暂存，保存响应落地后再基于最新共同基准重新判断，避免读写响应交错造成错误合并。线程被外部删除或读取失败时暂停自动保存并保留草稿，不自动重建线程。

### 5. node-diff3 只产出结构化结果，不生成冲突标记文件

vendored node-diff3，使用 `diff3Merge(local, base, remote)` 的结构化区块，而不是会生成 `<<<<<<<` 文本的字符串合并 API。相同修改按非冲突处理；只要存在冲突区块，就不写盘。

输入按“保留原始换行符的行”切分为数组，合并后直接连接，避免默认空白分词或统一换行导致 CRLF、末尾换行和整文件格式漂移。空文档、LF/CRLF、中文和相同修改需有独立用例。

无冲突时，只有当本地修订号仍与计算前一致才采用合并草稿；以外部指纹保存，成功后把合并内容设为新共同基准。若修订号已变化，丢弃本次结果并重新计算。更新 textarea 时保留可映射的选区，且不因无变化轮询重置光标或滚动位置。

有冲突时保存外部快照并暂停自动保存。冲突界面并排显示可编辑本地草稿和只读外部版本，用户可手工合并后确认“已解决并保存”，或明确选择采用外部版本。前者使用外部最新指纹提交，后者不执行写请求；两种操作都需更新共同基准后才恢复自动保存。

备选方案是 Yjs/Automerge，但任意外部文件写者不参与其共享历史与 provider，无法为当前场景提供等价保证。

### 6. 发布保持静态资源模式

将新增前端模块、三个库的官方浏览器分发文件及许可信息加入现有 vendor 管理和 `scripts/release.mjs` 资源清单。运行时不访问 CDN，不要求用户执行 npm install，也不新增 Node 服务依赖。现有发行校验继续检查精确文件清单和相对导入闭包。

## Risks / Trade-offs

- [轮询存在最长约 2.5 秒的可感知延迟] → 可见与聚焦时立即检查；接受这一延迟以换取无新增服务通道。
- [自动保存增加写请求和 P4 checkout 次数] → 800ms 防抖、无变化不保存、单在途请求和仅最新草稿续写。
- [三方合并无法识别语义冲突] → 只对文本无重叠冲突自动合并；重叠区域始终人工处理，并展示明确合并状态。
- [合并应用可能干扰光标或连续输入] → 以修订号作废旧结果、最小化内容更新并测试选区；无变化响应不触碰编辑器。
- [CRLF、空文件和末尾换行可能被合并库规范化] → 使用保留换行的行数组及专门回归测试，禁止直接默认字符串分词后统一拼接。
- [服务失联或外部删除导致内容无法保存] → 保留草稿、暂停自动保存并提供重试或冲突处理，不谎报成功。

## Migration Plan

无需数据迁移。按现有插件发布与兼容升级流程分发新版静态资源；旧 Markdown 文件、指纹和注册表保持原样。若需回滚，恢复旧前端与发行资源清单即可，期间已保存文件仍是普通 Markdown，不需要反向转换。
