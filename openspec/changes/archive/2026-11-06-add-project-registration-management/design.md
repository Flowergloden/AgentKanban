# Design

## Context

现有服务在单个 Node.js 进程内持有注册表 `Map`，通过临时文件加重命名原子写盘。`ensure({ root })` 同时服务于自动 hook 与显式打开，导致两种来源都调用同一个注册接口；Web 则把 URL 中的任意 root 放进本地项目列表，并在页面可见活动和加载项目时间接注册、初始化。需求契约见 `specs/kanban-viewer/spec.md`。

## Goals / Non-Goals

**Goals:**

- 用同一注册表持久化三态，并保证自动活动不会覆盖人工状态。
- 区分自动发现与 OpenKanban 显式确认，兼容旧宿主入口的降级行为。
- 让服务端而非仅前端执行初始化、写操作和 VCS 检测门控。
- 保持现有纯前端、本地单服务和原子文件写入架构。

**Non-Goals:**

- 不根据 `.git`、P4、目录名称或祖先目录自动推断真正项目根。
- 不建立永久黑名单之外的账户、权限或远程同步体系。
- 不自动清理旧记录，不为注册删除增加回收站。
- 不改变线程、便签及看板文件本身的数据格式。

## Decisions

### 1. 注册条目增加显式状态，缺失状态兼容为已注册

条目形状调整为 `{ lastSeen, state: 'pending' | 'registered' | 'ignored', vcs? }`。读取旧数字条目或缺少 `state` 的对象条目时填入 `registered`，规范化后的完整条目在加载时原子写回。忽略状态保留在注册表中，自动活动只续期服务，不刷新其项目 lastSeen，也不执行 VCS 检测。

选择显式三态而不是独立的待确认表和忽略表，可继续复用现有加载、去重、原子保存与重启保留路径。替代方案是用目录规则自动分类，但会误伤尚未初始化的真实项目，故不采用。

### 2. 新输入使用规范化绝对路径，手动新增额外检查目录

所有新注册和状态操作先要求绝对路径，再解析 `.`、尾斜杠和分隔符；Windows 使用大小写折叠后的规范键合并别名。旧注册表中的相对路径仅做兼容读取和既有斜杠归一化，不依赖服务当前工作目录改写为绝对路径。

手动新增在状态变更前检查目标是现存目录；OpenKanban 和待确认项确认只要求合法绝对路径，保持现有显式入口对尚未初始化路径的支持。选择统一规范键而不是同时保存显示路径和规范路径，避免引入第二套身份字段。

### 3. 自动发现与人工操作使用不同接口语义

保留 `POST /api/register`、`POST /api/activity` 和 `POST /api/heartbeat` 作为自动发现入口：新路径只建 `pending`，已有 `registered` 刷新 lastSeen，已有 `ignored` 不改变项目记录。

新增以下同源 JSON 写接口：

- `POST /api/projects/confirm`：将新路径、待确认或已忽略项目确认为 `registered`，供 OpenKanban、Web 确认及取消忽略复用。
- `POST /api/projects`：手动新增；额外验证现存目录后进入 `registered`。
- `POST /api/projects/ignore`：将待确认或已注册项目置为 `ignored`。
- `DELETE /api/projects`：按 root 删除任意状态的注册记录，不触碰项目文件。

`GET /api/projects` 返回全部状态，由管理界面使用；主项目选择器只投影 `registered`。新写接口沿用服务模式控制的同源与 JSON 校验，错误时返回明确状态，不执行部分操作。

### 4. OpenKanban 在确保服务后显式确认

为 `manager.ensure` 增加内部确认选项：普通 hook、活动恢复和控制启动仍走自动发现；`open.mjs` 使用确认选项，在服务健康检查及版本协调完成后调用确认接口，确认成功才打开浏览器。

新版 OpenKanban 连接旧协议服务时保留原有注册并打开的降级能力，因为旧服务没有状态概念。旧版 OpenKanban 连接新版服务时只会自动发现为待确认，用户可在新版 Web 中确认；不通过提高协议版本来强制停止可兼容的旧服务。

### 5. 注册写操作采用复制、落盘、提交

所有新增及修改注册表的操作在副本 `Map` 上完成，原子保存成功后再替换进程内状态；保存失败时保留原内存状态和磁盘文件。自动发现的既有写路径也统一到该提交助手，避免磁盘写失败后内存已提前变化。

单进程内请求串行到达提交助手即可满足当前架构；跨进程启动与升级仍由现有锁协调，不新增数据库或锁文件协议。

### 6. 服务端集中执行已注册门控

初始化和所有可能创建或修改 `kanban/` 的线程、活跃状态、便签及 VCS 写接口，在执行文件操作前检查规范 root 对应记录为 `registered`。待确认、已忽略和未登记路径返回明确错误。VCS 检测只在确认成功及已注册项目加载/刷新时执行。

该门控放在服务端共享层，而不是只隐藏前端按钮，防止旧页面、直接 URL 或手工请求绕过状态约束。

### 7. Web 分离项目身份、页面活动与初始化

前端保存完整项目列表，并派生已注册列表。页面活动仅在当前 root 已存在于注册表时携带 root；未知 URL 只用无 root 活动维持服务，不借页面活动创建待确认记录。

项目管理模态框按状态分区，提供新增、确认、忽略、取消忽略和删除。手动新增后不自动切换项目；用户明确打开项目时才进入项目页面。已注册项目缺少 `kanban/` 时显示初始化/忽略视图，不再于 root effect 中无条件调用 init。

删除或忽略当前项目后，选择下一最近已注册项目或空状态，并用 `history.replaceState` 清理或替换 root 参数。这样页面刷新不会重新引入已移除的 URL 上下文。

## Risks / Trade-offs

- [旧记录全部视为已注册，异常条目仍会立即出现] → 保留兼容并依赖本次管理界面一次性忽略或删除，不做猜测性清理。
- [已删除的活跃项目会再次出现为待确认] → 在管理界面说明删除与忽略的差异；需要抑制时发现者应选择忽略。
- [Windows 大小写折叠可能改变既有路径的显示形式] → 将其作为规范键迁移的一部分测试，保证所有 API 与 URL 使用同一规范值。
- [旧宿主与新服务混用时确认能力不对称] → 新入口对旧服务降级，旧入口对新服务仅发现；Web 提供补确认路径，不强杀兼容服务。
- [所有看板写接口增加门控可能暴露既有调用方未确认的问题] → 用显式 OpenKanban 和 Web 确认作为恢复路径，并覆盖直接 API 门控测试。

## Migration Plan

1. 新版服务首次加载注册表时，为所有旧条目补 `registered`，同时完成路径归一化和原子写回；写回失败则保留源文件并报告错误。
2. 服务端、OpenKanban 入口和 Web 作为同一发布包更新；运行中服务按现有兼容升级流程换代并保留注册表。
3. 用户打开项目管理界面，对既有临时目录或子目录执行忽略或删除；真实但未初始化的项目保持已注册，并显式选择初始化。
4. 回滚前先停止服务并备份新注册表。旧代码虽会忽略新增状态字段，但其后续写入可能丢失状态；需要保留三态时应在回滚后恢复备份。
